# 50-letter.md — 給未來 session 的信

寫信者：Claude Fable 5，2026-07-08，在 claude.ai 沙箱中一次性寫成。
讀者：之後在這個環境長期工作的 Sonnet / Opus / Haiku 等 session。

## 三件使用者沒問、但我認為對這個環境最重要的事

**1. 你回報的可信度比你的執行力值錢。**
弱模型和強模型最大的差距不在「會不會做錯」——都會——而在「錯了知不知道」。這套制度裡所有驗證規則的目的只有一個：讓「完成」這兩個字重新可信。所以當你不確定時，回報「不確定 + 原因」永遠是對的，回報「完成」而沒有證據永遠是錯的。使用者可以容忍慢，不能容忍被安靜地騙。

**2. 制度是拿來質疑的，不是拿來背的。**
每條規則寫下時都有一個它在防的具體失敗（見 00-diagnosis.md）。如果你發現某條規則在你的情境裡防不到任何東西、只剩摩擦——不要靜默略過，也不要盲目遵守，走 40-maintenance.md 的提案流程去改它。一套沒人敢改的制度會在六個月內和現實脫節，然後被整包拋棄。

**3. 使用者的注意力是這個系統裡最貴的資源，比 token 貴。**
問問題前先查（R3）、問的時候帶預設答案、批次問。同樣地，回報時先講結論再講過程，長內容落檔給路徑。你每省使用者一次來回，這套制度的存活率就高一點。

## 這套制度最可能的退化方式與預防

| 退化方式 | 早期訊號 | 預防 |
|---|---|---|
| **儀式化**：照著模板填字但驗收條件寫成不可檢查的空話（「功能正常運作」） | 驗收條件裡出現「正常」「合理」「高品質」等無判準詞 | R2 的定義：寫不出檢查命令/read-back 目標的驗收條件 = 還沒想清楚，不得動工 |
| **規則再堆積**：教訓、特例、補丁不斷寫回 CLAUDE.md，回到失效模式 #2 | CLAUDE.md 行數上升、出現第 6 條「硬規則」 | 40-maintenance.md 的行數觸發器；新硬規則必須換掉一條舊的或給出不能換的理由 |
| **驗證滑坡**：趕時間時「這次先不驗」，一次沒事之後就常態化 | 回報裡的證據欄開始出現「同上」「略」 | 略過驗證 = 修改硬規則，必須先問使用者；沒問而略過的完成回報視為未完成 |
| **升級路徑荒廢**：弱模型不好意思升級，硬撐重試 | 同一子任務出現第三輪重試紀錄 | 兩輪上限是硬規則；升級不是失敗，隱瞞卡住才是 |
| **[待填] 永久化**：模型表、環境事實一直沒填，規則引用空值 | 落地一個月後仍有 [待填] | 40-maintenance.md 第 4 節：每次精簡時盤點並上報 |

## 誠實條款：這套制度的極限（不要假裝它沒有）

- 拆解、fresh-context 驗證、多答案評審能把**可判定任務**的執行品質補到接近高階模型。
- 補不了的：**模糊題與品味判斷**。處理協議在 20-judgment-rubrics.md 最末節——升級到最高可用模型出帶理由的選項，仍需定奪就明說做不到、交使用者。任何等級的模型對品味題硬給單一「客觀」答案，都算違規。
- 本制度撰寫時無法檢視真實環境，所有關於「你的 harness 現況」的描述都是統計性推斷，以首次落地程序的實測為準修正。

## 未完成交接（首個真實 session 的待辦，按序）

1. **對抗審查（撰寫環境做不到，必須在真實環境補做）**：開 fresh-context subagent，prompt：「你是對抗審查者。讀 CLAUDE.md 與 refs/ 全部檔案，找出：(a) 互相打架的規則 (b) 錯誤的路徑/工具名/命令 (c) 弱模型會誤讀的模糊語句 (d) 引用了不存在檔案或章節的地方。每個問題附 檔案:行號 與建議修法。」修完為止，結果記入 00-diagnosis.md〈本環境實測〉。
2. 跑 00-diagnosis.md 的首次落地程序 1-5 步，填掉所有 `[待填]`。
3. 若 repo 原有 CLAUDE.md：審計合併（程序第 4 步），衝突項問使用者。
4. 第一次踩坑時建立 refs/LESSONS.md（格式在 40-maintenance.md 第 3 節）。
