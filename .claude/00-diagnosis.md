# 00-diagnosis.md — Harness 三大失效模式與首次落地程序

> 本檔由 Fable 5 於 2026-07-08 寫成。撰寫環境是 claude.ai 沙箱，**無法直接檢視使用者的實際 harness**，
> 因此本診斷是「幾乎所有 Claude Code harness 都會中的前三名」+ 可執行的審計步驟。
> 第一個真實 session 必須先跑本檔底部的〈首次落地程序〉，把審計結果寫回本檔的〈本環境實測〉區。

## 失效模式 #1：主對話直接吞大量原始內容（最漏 token）

**症狀判準（任一成立即中）：**
- 主對話裡出現整個檔案的 cat/Read 輸出超過 200 行（注意：委派規則的門檻是 100 行，見 10-dispatch；200 行是審計舊 session 用的保守偵測值），且後續只用到其中一小段。
- 主對話直接貼 web 搜尋結果全文、整包 git diff、整個 repo 的 grep 輸出。
- session 進行到一半，模型開始忘記早先的決定、重複問已回答過的事——這是 context 被原始資料擠爆的典型表現。

**為什麼致命：** 每個進入主對話的 token 都在稀釋 CLAUDE.md 規則與早期決策的注意力權重。弱模型受此影響比強模型更嚴重。

**修法（具體）：** 一切大量讀取派 subagent，主對話只收結論。規則見 `10-model-dispatch.md` 的「指揮官不下場」節。硬性判準：**預期輸出超過 100 行的讀取／搜尋／掃描，一律委派**。

## 失效模式 #2：CLAUDE.md 規則堆積與互相打架（最容易失焦）

**症狀判準：**
- CLAUDE.md 超過約 150 行或 1,500 tokens（用 `wc -l CLAUDE.md` 量）。
- 同一主題的規則出現在兩處以上，措辭不一致（例：一處說「commit 前跑測試」、另一處說「小改動可直接 commit」）。
- 存在無判準的抽象規則（「保持高品質」「小心處理」）——這些消耗載入預算但不改變任何行為。

**為什麼致命：** CLAUDE.md 每個 session 都載入，是最貴的不動產。規則互相打架時，弱模型不會報錯，會隨機挑一條執行。

**修法（具體）：** CLAUDE.md 只放路由與五條以內的硬規則，長內容抽成 `refs/` 引用檔（本包已照此結構重寫，見根目錄 `CLAUDE.md`）。維護時的增刪規則見 `40-maintenance.md`。

## 失效模式 #3：自寫自驗的完成幻覺（最容易出錯）

**症狀判準：**
- 模型宣稱「完成」但沒有附任何證據（測試輸出、read-back 內容、實跑結果）。
- 驗證由寫程式的同一個 context 執行——它會被自己的推理錨定，看不見自己的盲點。
- 驗收條件在動工之後才補寫（等於照著成品反推標準，必過）。

**為什麼致命：** 這是弱模型最常見的失敗放大器：執行錯誤本身不致命，「錯了卻回報成功」才致命，因為它污染後續所有決策。

**修法（具體）：** 驗收條件先寫、fresh-context agent 驗、證據落檔。規則見 `10-model-dispatch.md`〈驗證不自驗〉與 `20-judgment-rubrics.md`〈何時算真的完成〉。

## 首次落地程序（第一個真實 Claude Code session 必跑，約 15 分鐘）

按順序執行，每步結果寫進本檔底部〈本環境實測〉：

1. **盤點模型**：執行 `/model` 查看可用型號清單；查 `~/.claude/settings.json` 與專案 `.claude/settings.json` 是否有 `availableModels` 白名單或 `CLAUDE_CODE_SUBAGENT_MODEL` 環境變數。把實際可用型號填進 `10-model-dispatch.md` 的模型表 `[待填]` 欄。
2. **盤點 subagent**：執行 `/agents` 列出 built-in、user（`~/.claude/agents/`）、project（`.claude/agents/`）三層現有 agent。注意同名時 project 蓋過 user。
3. **盤點 MCP 與 skills**：執行 `/mcp` 列出已連接的 MCP server；檢查 `.claude/skills/` 或外掛 skills。填進 CLAUDE.md 的環境事實區。
4. **審計舊 CLAUDE.md（若存在）**：`wc -l` 量長度；逐條標記「有判準／無判準」「與新規則重複／衝突」。衝突項列清單問使用者裁決，不要自行合併。**改動前先 `cp CLAUDE.md CLAUDE.md.bak-<日期>`。**
5. **抽樣審計失效模式 #1**：翻最近 2-3 個 session 的 transcript（若有留存），數主對話裡 >200 行的原始讀取有幾次。>3 次即確認中招，優先執行委派規則。
6. **跑對抗審查**：開一個 fresh-context subagent，把本包全部檔案餵給它，任務照 `50-letter.md`〈未完成交接〉第 1 項的指令執行。這步在原撰寫環境做不到（無法開真正的 fresh subagent），是刻意留給真實環境的。
