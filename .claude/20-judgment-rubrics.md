# 20-judgment-rubrics.md — 判斷力外化

適用對象：任何等級的主對話模型。這些是原本靠「模型直覺」的判斷，改寫成可逐條核對的判準。
每條 rubric 附一個正例（✅ 該怎麼判）和一個反例（❌ 常見誤判）。

## R1. 何時該升級模型

**升級，若任一成立：**
- a. 現有模型在同一子任務已錯兩次（照 10-dispatch 第 5 節帶失敗軌跡升）。
- b. 任務需要跨 3 個以上模組/檔案的一致性設計決策，且錯了要大改。
- c. 任務有不可逆後果（刪資料、動 prod、對外發送）且無法先在沙箱驗證。
- d. 兩次產出互相矛盾、你無法判斷哪個對。

**不升級，若：** 只是任務量大（量大 = 拆小 + 便宜模型平行做，不是升級）；或只是你「感覺不安」但說不出違反上面哪條。

- ✅ 正例：sonnet 兩次修同一個 race condition 都讓另一個測試掛掉 → 符合 a，帶兩次 diff 與測試輸出升級 opus。
- ❌ 反例：要改 500 個檔案的 import 路徑，於是升級 opus「因為任務很大」。錯：這是機械模式，該寫成規則派 haiku 批次做。

## R2. 何時算真的完成

**完成 = 以下全部成立：**
- a. 動工前寫下的驗收條件，每條都有 fresh-context 驗收的證據（測試輸出/read-back 引文/實跑結果）。
- b. 沒有任何一條驗收條件被中途悄悄改寬。改驗收條件必須明寫「原條件 X 改為 Y，原因 Z」，且高風險任務要使用者同意。
- c. 產出落在講好的路徑，read-back 確認非空、非截斷。

**不算完成：** 「程式碼寫好了」「看起來沒問題」「上次跑過類似的」都不是證據。

- ✅ 正例：驗收條件是「`pytest tests/auth/` 全綠」，驗收 agent 實跑貼出 `24 passed`，附 commit hash → 完成。
- ❌ 反例：模型回報「已完成重構且行為不變」，但測試沒跑，理由是「改動很小」。改動大小與是否要驗證無關。

## R3. 何時該停下來問使用者

**必問，若任一成立：**
- a. 要做不可逆且影響範圍在工作目錄之外的事（push --force、刪遠端資源、寄信、動 prod 設定）。
- b. 兩條既有規則在此情境打架，且選錯的代價不對稱。
- c. 任務目標有兩種合理解讀，做錯方向要重做超過 30 分鐘的工。
- d. 高風險判斷的第二意見與第一意見衝突（見 10-dispatch 第 6 節）。

**不要問，若：** 答案能自己查到（檔案裡、docs 裡、跑個命令就知道）；或只是選項間差異很小、可逆、之後好改。問之前先把能查的查完，**問題要帶上你的預設答案**（「我打算選 A，因為…，反對請說」），一次批次問完。

- ✅ 正例：「清理舊資料」可解讀為刪 DB 列或封存到冷儲存，做錯要跑數小時的回復 → 符合 c，帶兩案與建議問使用者。
- ❌ 反例：不確定專案用 tabs 還是 spaces 就去問。錯：看兩個現有檔案就知道。

## R4. 什麼訊號代表方向錯了（該換路，而非重試）

**換路訊號（任一成立就停止當前路線）：**
- a. 每修一個錯就冒出一個新錯，連續兩輪（打地鼠 = 抽象層選錯了）。
- b. 為了讓方案成立，開始需要違反本制度的硬規則或專案既有慣例（「這裡先特例一下」）。
- c. 實作量遠超原估計（>2 倍）且沒有新資訊解釋為什麼。
- d. 你發現自己在對抗框架/函式庫的預設行為，而不是使用它。

**換路動作：** 停止產出程式碼 → 用 ≤10 行寫下「目前路線、卡住的本質、2 個替代路線」→ 按 R1 判斷是升級模型還是換方法 → 不確定就照 R3 問使用者。**重試同一路線的上限是兩輪，這是硬規則。**

- ✅ 正例：mock 第三方 SDK 修了兩輪、每輪都有新測試掛 → 符合 a，停下，改成在 SDK 邊界建薄封裝層，mock 封裝層。
- ❌ 反例：第三次微調同一個 regex 想通吃所有 edge case。錯：兩輪已用完，該換 parser 或列舉 case，而不是再賭一次。

## R5. 品質底線怎麼驗

不同產出的最低驗法（低於此標準的驗收無效）：

| 產出類型 | 底線驗法 |
|---|---|
| 程式碼修改 | 相關測試實跑全綠；沒有測試就先為改動行為補最小測試再改 |
| 新檔案/文件 | fresh-context read-back：驗收 agent 讀檔逐條核對驗收條件並引用原文 |
| 研究/搜尋結論 | 每個關鍵事實附來源（檔案:行號 或 URL）；抽查其中 2 個來源屬實 |
| 批次改檔 | 抽樣 3 處 read-back + 全量跑一次能偵測此類錯誤的檢查（編譯/測試/lint） |
| 高風險判斷 | 上述之外，再加第二意見或多答案評審（10-dispatch 第 6 節） |

- ✅ 正例：批次改 40 個檔的 API 呼叫 → 抽 3 檔 read-back + 全 repo 編譯 + 跑受影響測試。
- ❌ 反例：研究任務回報「業界普遍做法是 X」但沒有任何來源。無來源的結論一律當作未驗證假設處理。

## 本制度的極限（誠實條款）

拆解、驗證、多樣本評審能補**執行品質**；補不了**模糊題與品味判斷**（例：兩個都能跑的架構哪個十年後好維護、文案哪版語氣對、產品該不該做某功能）。遇到這類問題：
1. 先確認它真的是品味題（試著寫出可檢查的判準；寫得出來就不是品味題，照常流程走）。
2. 是品味題 → 升級到本環境最高可用模型出 2-3 個帶理由的選項。
3. 仍需定奪 → 明說「這是判斷題，制度補不了」，交使用者或外部第二意見裁決。**禁止**弱模型對品味題硬給單一答案並包裝成客觀結論。
