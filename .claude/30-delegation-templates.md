# 30-delegation-templates.md — 派工 prompt 模板

用法：複製對應模板，填掉 `{…}` 空格，整段作為 subagent 的任務 prompt。
每個模板都內建派工三件套（目標與動機／驗收條件／回報格式）與回報合約。
模型選擇照 `10-model-dispatch.md` 第 3 節的分派表；模板首行的建議只是預設。

**所有模板共用的固定尾段（每次都附上，不要省）：**

```
回報合約：
- 只回結論（≤10 行）+ 關鍵位置（檔案:行號）+ 驗收條件逐條核對（過/不過 + 一行證據）。
- 長產物寫到 {輸出路徑}，回報只給路徑。
- 沒找到或做不到就直說並附原因；禁止推測填空、禁止回報未驗證的成功。
- 回報你實際使用的模型。
```

---

## T1. 搜尋（建議 haiku 級）

```
目標：在 {範圍，例：整個 repo / src/ 目錄} 找出 {明確標的，例：所有呼叫 loadUser() 的位置}。
動機：{為什麼要找，例：準備改它的簽名，需要知道全部呼叫點}。
方法提示：{可選：建議的 grep pattern / 檔名 glob}。
驗收條件：
1. 每個結果都有 檔案:行號 + 一行上下文摘要。
2. 若結果 >{30} 筆，列前 {30} 筆並註明總數與統計方式。
3. 明確回報搜尋過的範圍與用過的 pattern（讓「零結果」可被信任）。
輸出路徑：{完整清單落檔到 …；≤10 筆可直接回報}
```

## T2. 實作（建議 sonnet 級）

```
目標：實作 {功能描述}，位置在 {檔案/模組}。
動機：{這個功能為誰解決什麼問題；遇到規格沒寫到的情況時，往這個動機的方向判斷}。
限制：遵守專案慣例（先看 {1-2 個參考檔} 的寫法）；不改動 {不可碰的範圍}；不新增依賴除非回報說明。
驗收條件（動工前已定案，不得中途放寬）：
1. {測試命令，例：pytest tests/xxx/} 全綠。
2. 新行為有對應的新測試：{列出至少要覆蓋的 case}。
3. {其他可檢查條件，例：public API 簽名不變}。
輸出路徑：改動的檔案清單 + diff 摘要落檔到 {…}
```

## T3. 重構（建議 sonnet 級）

```
目標：把 {對象} 從 {現狀} 重構為 {目標形態}。
動機：{現狀的具體痛點}。
硬限制：外部可觀察行為不變——這是重構的定義，違反即失敗。
步驟要求：先確認現有測試全綠並記錄基線（{測試命令}）；小步改、每步可跑；發現測試覆蓋不足，先補測試再重構。
驗收條件：
1. 重構後 {測試命令} 結果與基線一致（同樣全綠、無新略過）。
2. {結構性判準，例：xxx.py 不再 import yyy / 檔案行數 < N / 該類只剩單一職責}。
3. 無行為變更：不新增功能、不修 bug（發現 bug 記下來回報，不要順手修）。
輸出路徑：diff 與基線/重構後測試輸出落檔到 {…}
```

## T4. 研究（建議 sonnet 級；純文件檢索可 haiku 級）

```
目標：回答 {明確的問題，最好可判定，例：函式庫 X 的 v3 是否支援 streaming？怎麼用？}。
動機：{這個答案會決定什麼，例：決定我們要不要升版}。
來源優先序：{官方文件 > 原始碼 > issue 討論 > 部落格}；標注每個來源的日期。
驗收條件：
1. 每個關鍵結論附來源（URL 或 檔案:行號）。
2. 區分「來源明說的」與「你推論的」，推論要標注。
3. 找不到明確答案時，回報查過哪些來源與各自說了什麼，不要硬給答案。
輸出路徑：完整筆記落檔到 {…}，回報只給 ≤10 行結論。
```

## T5. 審查（建議 sonnet 級；必須是 fresh-context，不可由執行方兼任）

```
目標：審查 {對象：diff / 檔案 / PR}，你沒有參與它的產出，請以懷疑立場獨立驗證。
動機：{這份產出接下來的用途與風險等級}。
審查清單：
1. 驗收條件逐條核對（原始條件如下，逐條給 過/不過 + 證據）：{貼上動工前的驗收條件}
2. 正確性：實跑 {測試/命令}，貼輸出摘要；不接受未實跑的「看起來對」。
3. {專案特定關注點，例：有無 N+1 查詢 / 有無把祕密寫進 code / 錯誤處理}。
驗收條件（對審查本身）：
1. 每個發現的問題附 檔案:行號 + 嚴重度（block / should-fix / nit）+ 建議修法。
2. 結論只能三選一：通過 / 有條件通過（列條件）/ 退回（列 block 項）。
輸出路徑：完整審查報告落檔到 {…}
```
