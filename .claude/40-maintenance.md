# 40-maintenance.md — 制度檔案維護協議

適用對象：未來所有 session 的模型（含弱模型）。本檔規定誰能改什麼、怎麼改、教訓怎麼記。

## 1. 權限分級

**可自行改（不必問使用者）：**
- 修正客觀事實錯誤：錯的路徑、工具名、命令、失效連結。改前備份，改後在 commit/回報中註明。
- 填 `[待填]` 欄位（用實測結果，附查證方式）。
- 在 LESSONS.md 追加教訓（照第 3 節格式）。
- 為既有規則補充例子（不改變規則語義）。

**改之前必須先問使用者（帶提案與理由）：**
- 新增、刪除、放寬任何硬規則（CLAUDE.md 五條、重試上限、驗證不自驗、升級判準）。
- 調整模型分派表的預設（例：把實作預設從 sonnet 降到 haiku）。
- 重構檔案結構（合併/拆分/改名 refs/ 下的檔案）。
- 任何「這條規則在此情境不適用所以我略過」——略過即修改，先問。

**永遠不可做：**
- 無備份覆蓋既有檔案（硬規則 4）。
- 因為規則「不方便」而靜默不遵守。規則不合理 → 走上面的提案流程。

## 2. 修改程序（三步，缺一不可）

1. 備份：`cp <檔> <檔>.bak-<YYYYMMDD>`（.bak 檔累積超過 5 份可刪最舊的）。
2. 修改，並在檔案頂部的變更記錄加一行：`<日期> <改了什麼> <為什麼>`（無變更記錄區就建一個）。
3. fresh-context read-back 驗證：新內容完整、與其他檔案無新矛盾（至少核對 CLAUDE.md 路由表與被改檔的交叉引用）。

## 3. 踩坑教訓的記法

**寫到哪：** `refs/LESSONS.md`（首次踩坑時建立）。CLAUDE.md 的〈教訓摘要〉只放其中最高頻的 ≤10 條一行版。

**格式（每條固定四欄）：**

```
### <YYYYMMDD> <一句話標題>
- 情境：什麼任務、什麼條件下發生
- 錯誤行為：模型實際做了什麼、造成什麼後果
- 正確行為：下次遇到同情境該怎麼做（要具體到可執行）
- 制度修改：有無因此改規則？改了哪檔哪條；沒改就寫「無」
```

**什麼算值得記：** 同類錯誤第二次出現、或單次錯誤代價超過 30 分鐘返工。一次性的小手滑不記，避免噪音淹沒訊號。

## 4. 精簡節奏（防止制度自己變成失效模式 #2）

- LESSONS.md 超過 **40 條** 或 **400 行** → 觸發精簡：把同類教訓合併、已寫進正式規則的條目刪除（規則本身就是它的紀念碑）。精簡是刪除行為，走「先問使用者」流程，帶精簡前後對照。
- CLAUDE.md 超過 **80 行** → 觸發瘦身提案（80 行是新制度的維護門檻；00-diagnosis 的 150 行是診斷舊檔的病態門檻，兩者用途不同）：把長出來的內容抽回 refs/。
- 任一 refs/ 檔超過 **250 行** → 檢討是否拆分或刪冗，提案處理。
- 每次觸發精簡時順便檢查：有沒有 `[待填]` 放了超過一個月沒填？有 → 列給使用者。
