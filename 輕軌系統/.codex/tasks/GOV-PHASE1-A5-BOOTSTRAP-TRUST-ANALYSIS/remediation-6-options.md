# Remediation 6 Options

Status: `OPTIONS ONLY — REMEDIATION 6 NOT AUTHORIZED OR CREATED`

## Decision summary

All viable options require a newly authorized Remediation 6 because the current 97-file candidate has six blocking findings. Any changed or reduced candidate then requires a fresh independent A6. A5 remains immutable `ARCHIVED / BLOCKER`.

The recommended option is **Option 2 — Bootstrap convergence**. It resolves the circular trust problem directly, keeps a useful minimum governance core, and avoids implementing a staged-proof authority before any trusted governance base exists.

## Option 1 — Full correction

### Scope

Retain the current minimum-core ambitions and fully implement:

- actor-mandatory six-source scope consumption;
- anchored WORKSPACE_CANDIDATE provenance;
- typed scope/preapproval receipts;
- same-execution live STAGED_EXACT index validation;
- malformed-safe scanner canonicalization and full declared matrix;
- production-consumer mutation/oracle architecture;
- typed meta-rule classification and namespace-independent Domain exclusion;
- full lifecycle predecessor automaton or a formally chosen narrowed lifecycle model.

### Effect

- **A5 findings addressable:** all seven through implementation, with the lifecycle finding closed or explicitly narrowed.
- **Residual risks:** procedural human/Reviewer identity, no OS sandbox/DLP, shell/executable/TOCTOU, remote Git enforcement absent.
- **Candidate manifest:** must be rebuilt; likely similar to or larger than 97 because new proof receipts, rule classification, production exploit tables, and mutations add artifacts. No responsible exact count exists before dependency enumeration.
- **Migration 320:** remains `NO-GO`; no Domain authority is added.
- **Remediation 6 required:** yes.
- **A6 required:** yes.
- **First commit human effort:** high. Humans must still independently bootstrap the untrusted implementation, verify exact staging, and record the first commit anchor.
- **Steady-state expansion cost:** lowest after successful implementation because most intended automation already exists.

### Risk

The authority surface remains large. A split between helper, consumer, proof issuer, and test oracle can recur. Full implementation does not eliminate the need for a human bootstrap Gate because all new code is still untrusted before the first commit.

## Option 2 — Bootstrap convergence (recommended)

### Scope

Create a smaller first-commit contract:

- implement actor-mandatory scope consumption;
- implement malformed-safe minimal scanner behavior and exact production tests;
- remove generic meta-rule applicability from bootstrap and retain selected controls as static policy;
- retain proposed-only Domain registry;
- treat workspace candidate hashes as evidence-only;
- remove STAGED_EXACT and generic execution-proof authority from bootstrap;
- narrow lifecycle to informational snapshot projection or remove it from Gate claims;
- introduce Bootstrap Candidate Review and Bootstrap Human Commit Gates;
- human verifies/stages/commits the exact first candidate;
- enable typed candidate/staged proof only for later changes executed from the trusted base commit.

### Effect

- **A5 findings addressable:** scope and scanner findings by implementation; fixture findings by production-oracle redesign; Domain finding by removing dynamic meta authority; staged-proof finding by removing it from bootstrap and defining anchored steady-state re-entry; lifecycle by narrowing.
- **Residual risks:** procedural identity, human bootstrap workload, no OS sandbox/DLP, shell/executable/TOCTOU, no remote Git controls. These are explicit and do not create GO inside the narrowed contract.
- **Candidate manifest:** must be rebuilt and should decrease from 97 after removing staged-proof authority, dynamic meta-rule authority, optional lifecycle/advanced scanner paths, and nonessential test infrastructure. Exact count depends on dependency closure; preserving 97 is prohibited as an objective.
- **Migration 320:** remains `NO-GO` and proposed-only.
- **Remediation 6 required:** yes.
- **A6 required:** yes.
- **First commit human effort:** high but bounded: inspect exact manifest, confirm Reviewer set, independently stage/compare, commit, and record anchor.
- **Steady-state expansion cost:** medium. Typed proof and live execution Gate are added later against a trusted base.

### Why recommended

It acknowledges the bootstrap trust boundary rather than simulating trusted provenance with mutable fields. It also keeps scope, review, manifest, minimal scanning, and proposed-only Domain governance useful from the first commit.

## Option 3 — Extreme minimal governance baseline

### Scope

First commit only the dependency-closed minimum needed for:

- AGENTS.md;
- Phase Policy and residual risks;
- Agent role definitions;
- read-only Reviewer workflow;
- actor-mandatory scope validator;
- minimal manifest scanner;
- proposed-only Rule registry;
- Bootstrap Candidate and Human Commit instructions.

Remove from the bootstrap candidate:

- typed candidate and staged proof schemas/generators/consumers;
- lifecycle projection and event machinery;
- dynamic meta-rule registry;
- advanced scanner normalization/entropy/header/magic claims not essential to the minimal reject list;
- generic task-generation/templates not needed for review;
- large fixture/concurrency infrastructure, retaining only exact production exploit tests for included controls.

### Effect

- **A5 findings addressable:** proof, lifecycle, advanced scanner, and meta-rule findings are removed from the bootstrap contract; scope still requires implementation; minimal scanner and its oracle must match exactly.
- **Residual risks:** greatest reliance on human procedure; minimal automation; procedural identity; platform risks. No removed feature may leave an alternate GO path.
- **Candidate manifest:** must be rebuilt and should be substantially smaller than 97. A rough qualitative expectation is a few dozen dependency-closed governance files, but no numeric commitment should be made before exact enumeration.
- **Migration 320:** remains `NO-GO`.
- **Remediation 6 required:** yes, because removal changes schemas, policies, manifest, and consumers.
- **A6 required:** yes.
- **First commit human effort:** moderate by file count but high in responsibility because fewer automatic checks are authoritative.
- **Steady-state expansion cost:** highest; each deferred capability needs a later design, implementation, independent review, and anchored rollout.

### Risk

Over-removal can leave an unusable framework or shift too much to undocumented human practice. The minimal baseline must still specify exact bootstrap steps, fail-closed scope, Reviewer independence, and manifest integrity.
