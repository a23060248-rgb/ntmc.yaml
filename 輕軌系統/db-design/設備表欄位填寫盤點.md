## B. 不是「表單填」的欄位（系統自動／其他流程）

這些**不該手動填**，盤點時要排除，否則會誤判：

| 欄位 | 來源 |
|------|------|
| systemCode／categoryCode／sequenceNo／typeCode | 由料號自動拆解(50.83.0001.LO → 50／83／0001／LO) |
| 庫存分布(可發／已領出／使用中／不可用) | 由庫存異動(領料／入庫／調撥／報廢)累積 |
| 用料履歷(111–114) | 由匯入或庫存異動自動產生 |
| 設備別名 | 由「設備別名對應」功能維護 |

## C. 結構性問題（比單一欄位更關鍵）

1. **雲端明細沒有編輯入口** —— 你從「物料清單(雲端)」點開的明細(`openMaterialDetail`)只有「領料／設備別名對應」，**沒有「編輯／補資料」按鈕**。要編輯只能走另一條原型路徑。
2. **兩套表單不一致**：
   - 「新增 API 物料」(雲端查詢面板)→ 系統別／分類／屬性／單位全是**自由打字**，不接清單 → 資料會亂。
   - 「補齊物料資料」(`openMaterialEditModal`)→ 用**下拉接清單**(好)，但掛在原型明細頁、且缺序號管理／細分類／廠牌／型號。

## D. 三層缺口總整理

**Schema(要加欄位)**
- `brand` 廠牌、`model` 型號
- 照片：`photo_url`(簡單)或另開 `material_attachment` 表(完整)

**API(POST/PATCH 要接受)**
- `categoryName` 細分類(欄位已有資料，只差 API 開放寫)
- `brand`、`model`(等 schema 加好)
- 照片欄位

**表單／UI**
- 雲端明細加「編輯」按鈕 → 開可寫雲端的表單
- 統一成**一套表單**(新增＋編輯共用)，系統別／屬性／單位／(細分類)一律**下拉接清單**
- 補欄位：序號管理、細分類、廠牌、型號
- 照片上傳
- (用料履歷靠匯入，手動補一筆當次要功能)

## E. 建議調整方案（一套表單打通）

1. **做一個「物料主檔編輯」表單**，分組呈現，新增與編輯共用：
   - **基本**：料號(新增可填/編輯唯讀)、名稱、規格、廠牌、型號、單位(下拉)
   - **分類**：系統別(下拉15項)、細分類、物料屬性(下拉)、物料分類
   - **管理參數**：安全等級、序號管理、可修件、請購點、交期、市售品
   - **採購／備註**：預估單價、檢討說明
   - **照片**：上傳區
2. **掛到雲端明細**：明細加「編輯」按鈕開這張表單，存檔 PATCH 雲端。
3. **後端配合**：schema 加 brand／model(＋照片)；API POST/PATCH 接 categoryName／brand／model／photo。
4. 照片先用最簡單方式(URL 或 base64 存欄位)，之後再升級物件儲存。

> 動工順序建議：先做「表單＋雲端明細編輯入口」(UI，效益最高、不動 schema 的欄位先通) → 再補 schema(brand/model/photo) → 最後照片上傳。
